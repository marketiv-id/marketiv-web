# ADR-007 — Minimum Withdraw Dipasang sebagai Konstanta Sistem (= Rp50.000)

## Status

Diterima — **diubah sebagian oleh implementasi** (catatan 2026-10-12).

> **Catatan verifikasi 2026-10-12:** nilai Rp50.000 tetap berlaku, tetapi penegakan server di `request-withdrawal` membaca **environment variable** `MINIMUM_WITHDRAW` (default `50000`) — yaitu opsi 2 di bawah, bukan konstanta murni. Pesan error juga dibentuk dinamis dari nilai tersebut. Tetap tidak ada koleksi settings, endpoint, atau UI admin.

## Context

- Modul Payments butuh aturan batas bawah penarikan saldo (minimum withdraw) untuk menutup biaya transfer manual admin dan mencegah spam request kecil.
- Sebelum ADR ini, dokumentasi inkonsisten: workflow menyebut `MINIMUM_WITHDRAW` sebagai "konstanta sistem", sedangkan `Payments/70_Backend.md` menyebutnya "konfigurabel". Tidak ada koleksi `app_settings`, tidak ada endpoint admin, dan tidak ada UI admin untuk mengubah nilai.
- Tiga opsi yang dipertimbangkan:
  1. Hardcode sebagai konstanta di Appwrite Function.
  2. Environment variable Appwrite Function (bisa diubah tanpa redeploy kode, tapi tanpa UI admin).
  3. Koleksi `platform_settings` + halaman admin Settings (paling fleksibel, tapi butuh koleksi, API, dan UI baru).

## Decision

Minimum withdraw dipasang sebagai **konstanta sistem** dengan nilai tetap `Rp50.000` (`50.000`).

- Dideklarasikan sebagai konstanta di service layer (`wallet.service.ts`).
- Tidak ada koleksi database, environment variable, maupun endpoint admin untuk mengubah nilai.
- Pesan error ke user dan label UI menggunakan string literal `"Rp50.000"` — bukan variabel dinamis.
- Perubahan nilai di masa depan mensyaratkan update kode + redeploy Function.

## Consequences

- (+) Implementasi paling sederhana — satu konstanta, tidak ada koleksi/API/UI baru.
- (+) Tidak menambah surface area keamanan (tidak ada endpoint/settings yang bisa disalahgunakan).
- (+) Perilaku deterministik dan mudah diuji (nilai tidak berubah antar-deploy tanpa eksplisit).
- (−) Perubahan nilai butuh siklus deploy — bukan fitur operasional harian.
- (−) Tidak fleksibel untuk eksperimen A/B atau penyesuaian regional.
- (Lihat juga) [`Payments/30_Business_Rules.md`](../02_Modules/Payments/30_Business_Rules.md), [`Payments/60_API.md`](../02_Modules/Payments/60_API.md), [`Payments/70_Backend.md`](../02_Modules/Payments/70_Backend.md), [`Workflows/50_Withdrawal.md`](../03_Workflows/50_Withdrawal.md).

### Catatan implementasi (2026-10-12)

| Lokasi | Bentuk |
|---|---|
| `00_BACKEND/functions/request-withdrawal/src/main.js` (penegak otoritatif) | `env.minimumWithdraw = Number(process.env.MINIMUM_WITHDRAW \|\| 50000)`; error `Minimum penarikan Rp${minimumWithdraw.toLocaleString("id-ID")}` |
| `00_BACKEND/src/services/wallet.service.ts` | `export const MINIMUM_WITHDRAW = 50000` (referensi) |
| `src/types/domain.ts` → `src/lib/validations/withdrawal.schema.ts` | `MINIMUM_WITHDRAW = 50_000`, validasi Zod di frontend |

- (−) Nilai server dapat diubah lewat env Console tanpa redeploy, sementara frontend tetap 50.000 hardcoded — keduanya bisa menyimpang bila env diubah.
- Guard penarikan lain yang juga berbasis env (bukan bagian keputusan ini): `KYC_THRESHOLD`, `WITHDRAW_PER_DAY_LIMIT`, `WITHDRAW_COOLING_DAYS`, `WITHDRAWAL_ADVANCED_GUARDS_ENABLED` (lihat [50_Withdrawal](../03_Workflows/50_Withdrawal.md)).
