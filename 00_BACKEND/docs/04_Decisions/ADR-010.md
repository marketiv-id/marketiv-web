# ADR-010 — Campaign Submission Validation Authority pada Admin Marketiv

## Status

Diterima — **diimplementasikan di backend dan admin app** (catatan 2026-10-12). Sisa: audit log terstruktur dan tampilan sinyal fraud di antrean Admin belum ada.

> **Catatan verifikasi 2026-10-12:** status lama "backend authorization wiring pending" sudah tidak berlaku. `review-submission` kini hanya menerima Admin aktif, ada antrean `get-admin-submission-queue`, periode observasi views, dan views terkunci (`views_final`). Admin app terpisah ada di `admin/` (`admin/src/features/admin/submissions`). Pola yang sama diperluas ke deliverable Rate Card (`review-ratecard-deliverable`).

## Context

- Campaign PPV membutuhkan satu authority yang menentukan apakah bukti tayang Creator valid dan berapa views final yang menjadi dasar reward.
- Implementasi lama menempatkan UMKM sebagai reviewer submission dan penginput views.
- Model tersebut menambah beban operasional UMKM, berisiko menghasilkan standar validasi berbeda antar-UMKM, dan menghubungkan user buyer langsung ke keputusan yang memicu reward finansial.
- Marketiv sudah memiliki arah Admin dashboard untuk operasi submission review.
- Permission/feature contract yang lebih baru juga menempatkan validation sebagai Admin/trusted operation.
- Current `ai-fraud-precheck` hanya menghasilkan risk metadata; ia tidak perlu menjadi authority final.
- Current backend `review-submission` masih memeriksa ownership UMKM dan harus dimigrasikan pada tahap backend terpisah. *(Tidak berlaku lagi per 2026-10-12 — lihat Catatan implementasi.)*

## Decision

1. **Creator** mengirim bukti tayang berupa public post URL untuk claim miliknya.
2. Submission dibuat sebagai `pending` melalui trusted Function.
3. **Admin Marketiv** menjadi satu-satunya user-facing authority untuk:
   - membuka review queue;
   - memeriksa bukti;
   - menangkap/mengunci final views;
   - mengambil keputusan `approved` atau `rejected`;
   - memberi catatan/alasan.
4. **UMKM** dapat membaca submission milik campaign-nya, tetapi tidak dapat approve, reject, atau mengubah views.
5. `fraudStatus` diperlakukan sebagai **risk signal terpisah** dari `submission.status`. Fraud precheck membantu Admin memprioritaskan review, tetapi keputusan finansial final berasal dari submission validation authority.
6. Semua perubahan status/final views dilakukan melalui trusted backend/Appwrite Function, bukan direct client database write.
7. Reward Campaign tetap dihitung backend setelah status authoritative menjadi `approved` dan menggunakan locked views. Campaign platform fee tetap buyer-side sesuai ADR-008.
8. UI Creator/UMKM dimigrasikan lebih dahulu; backend Admin authorization dilakukan pada change set terpisah dengan security tests dan E2E verification.

## Consequences

- (+) Satu standar validasi berlaku untuk seluruh Campaign.
- (+) UMKM mendapat UX lebih sederhana: membuat campaign dan memantau hasil, bukan menjadi operator audit.
- (+) Keputusan yang memicu reward lebih mudah diaudit karena melalui Admin/trusted Function.
- (+) AI fraud dapat tetap advisory tanpa sendirian memicu payout.
- (+) Admin dashboard menjadi control plane operasional yang jelas.
- (−) Marketiv membutuhkan kapasitas operasional Admin untuk review submission MVP.
- (−) Backend `review-submission`, permissions/read path, audit log, dan Admin authentication harus dimigrasikan sebelum E2E dianggap selesai.
- (−) Dokumentasi lama yang menyebut UMKM sebagai validator harus diperbarui serentak.

### Catatan implementasi (2026-10-12)

Sudah ada di kode:

- `submit-campaign-proof` membuat submission `pending` (read: kreator + UMKM pemilik campaign) — butir 1–2.
- `get-admin-submission-queue` + `review-submission` (Admin aktif) — butir 3. `approved` mewajibkan `views` dan periode observasi `VIEW_VALIDATION_DELAY_HOURS` (default 72 jam); mengunci `views_count`, `views_captured_at`, `views_source: "manual_admin"`, `views_final: true`; menyimpan `reviewNotes`. `rejected` mengembalikan kuota claim.
- UMKM tidak punya aksi review di frontend — butir 4.
- `ai-fraud-precheck` tidak mengubah `submission.status` — butir 5.
- `calculate-campaign-reward` memakai `views_count` bila `views_final` — butir 7.

Belum / berbeda:

- **Audit log**: tidak ada koleksi audit; jejak keputusan hanya kolom submission (`reviewNotes`, `views_*`) + log Function. Identitas Admin yang memutus **tidak** disimpan di submission (berbeda dengan `ratecard_deliverable_validations.reviewedBy`).
- **Prioritas berbasis risiko**: DTO antrean belum memuat `fraudScore`/`fraudStatus`.
- **Otorisasi Admin**: dicek di Function (`users.role = "admin"` + `status = active`, atau akun Auth berlabel `admin`). `review-submission` dan `get-admin-submission-queue` juga menerima `prefs.role = "admin"` pada akun Auth — prefs dapat ditulis user sendiri, sehingga jalur ini lebih lemah daripada `review-withdrawal` (label saja).
- **Butir 6**: `campaign_submissions` masih punya `create("users")` di level koleksi; penulisan langsung dari klien di luar Function belum ditutup di konfigurasi.
